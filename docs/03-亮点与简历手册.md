# CostLens 亮点与简历手册

> 配套文档：[01-业务方案.md](01-业务方案.md)。所有口径、数字与业务细节以 01 为准。
> 体量定位：个人副业级，月均约 40 单。全部表述按此量级自洽，不涉及并发与吞吐。

---

## 1. 一句话定位

> CostLens 是一个跨境电商全成本核算与定价决策系统：把三个市场的运费、平台佣金、支付费等异构费率规则统一成可版本化的计算模型，回答"这一单到底赚了多少、亏在哪一项"。
> 定价方向上把它反解成方程——给定目标毛利求售价，并判断在平台核价上限下是否可行。

1、抽象三市场运费计费范式：美国 = 计费重（进位 0.5kg）× Zone 阶梯单价，连续线性；日本按三

价，1000 组随机参数全部收敛。

## 4. 每条亮点的三层深挖问答

追问的递进逻辑固定为三层：**Q1 问"为什么不直接那么做"（方案必要性）→ Q2 问机制细节（是否真懂规则）→ Q3 问边界与代价（是否真做过）**。

### 亮点 1 · 多市场计费范式抽象

**Q1（浅）：三个市场运费不一样，多配几个字段不就覆盖了？**
A：差异在数学结构不在参数。美国是"重量 × Zone 单价"的连续线性，日本是"三边和 → Size 档 → 地帯价"的阶跃查表，东南亚是"首重 + 续重向上取整"。字段集合都不同（日本根本没有体积重概念），合表只能靠大量 NULL 硬撑，每加一个市场改一次表结构。

**Q2（中）：你说"重量在三个市场角色不同"，具体是什么？**
A：美国重量是直接相乘的计价因子；日本重量只做上限校验，超了才升级档，不参与金额计算；东南亚重量驱动取整次数，是步长。同一字段在三处分别是因子、约束、步长，这层差异只能放到实现里，塞进参数必然算错。

**Q3（深）：抽象之后新增一个市场的成本？边界正确性谁来保证？**
A：新增一个实现类 + 一张独立费率表，主流程和落库结构不动。代价是每个实现要独立承担边界正确性，所以定了铁律：金额用最小货币单位整数、重量用整数克、尺寸用整数厘米，并用 ArchUnit 禁止 `double`/`float` 进入计价路径。

### 亮点 2 · 平台费用异构核算

**Q1（浅）：佣金为什么不直接算售价 × 费率？**
A：真实佣金有三层修饰：类目差异（15% / 8% / 17%）、每笔最低 $0.30、超 $250 部分仅 5%。$1 商品按 15% 得 $0.15，实收 $0.30。低价轻小件几乎全部踩在这条线上，这就是"表上 20% 毛利、实际为负"的直接来源。

**Q2（中）：最低收费在什么情况下让费率翻倍？**
A：只要"售价 × 费率 < floor"就成立，临界售价 = floor / 费率。按 15%、$0.30 算是 $2.00。所以 $1 商品实际费率 30%，$0.50 商品是 60%——低价段的有效费率不是常数，而是 floor / 售价的反比曲线。

**Q3（深）：那你定价时怎么处理这个分段？**
A：把佣金写成售价的分段函数，临界点（$2.00、$250）把价格轴切成若干区间，区间内线性；逐段解析求解，再回代校验解是否真落在该区间，不落就换段；全部段落空则判"目标毛利不可达"并给出最接近的可达点。

### 亮点 3 · 双时态历史重算

**Q1（浅）：为什么不能直接改费率表？**
A：直接 UPDATE 会让历史重算结果跟着变。之前基于旧费率做的定价决策就永久不可复现——复盘时无法回答"我当时是怎么认为的"。丢的不是数据，是认知状态。

**Q2（中）：加个版本号 + 一张历史表不够吗？**
A：版本号只有一条时间轴，能回答"现在用第几版"，但回答不了两个不同问题："2023-03-15 业务上适用哪条费率"和"截至 2023-03-20，系统认为 3-15 适用哪条"。所以要拆成 valid time 与 transaction time 两条轴，as-of 查询同时约束两者。

**Q3（深）：双口径重算的实际价值在哪？**
A：原时点口径回答"当时算得对不对"，现行口径回答"按今天的规则重跑会差多少"，两者之差就是政策变更对历史成本的影响额，且能拆到费用项级。平台补扣退费要求在**原账期**调整，没有这个能力，月度毛利曲线会跳变，看不出真实趋势。

### 亮点 4 · 定价反推与核价约束

**Q1（浅）：定价不就是成本 ÷ (1 − 费率) 吗？**
A：只在佣金是纯比例时成立。实际佣金含最低收费和金额阶梯，是分段函数；支付费是比例 + 固定额。`f(售价) = 0` 是分段方程。直接除算在低价段会低估成本、定价偏低，卖得越多亏得越多——我的手机壳生意就是这么亏掉的。

**Q2（中）：最低收费让方程退化成什么样？**
A：在"售价 × 费率 < floor"区间里佣金恒等于 floor，`f` 退化成斜率为 1 的直线，解可以直接写出，但必须回代校验该不等式是否成立。不成立说明假设区间错了，要换段重解——这就是为什么必须"枚举 + 校验"，不能一次解完。

**Q3（深）：核价上限为什么当约束而不是直接截断？**
A：截断会静默返回一个达不到目标毛利的价。正确做法是把 `x* ≤ 上限` 当约束一起判断：可行返回解，不可行返回"还差 ¥3.20 才能达到 25% 毛利"这类缺口。输出"不可行"比输出一个错价更有价值，至少能立刻判断这个品不该上。

## 5. 高频追问问答（10 个）

**Q1：月均几十单，值得写一套系统吗？**
A：不是为单量写的，是为"算不准"写的。40 单/月 Excel 也能算，问题是三市场三套规则、改一个参数要重算三张表、出错定位不到费用项。系统解决的是规则建模与可复现性，与单量无关；单量小反而让我能穷举验证正确性，而不是靠抽样。

**Q2：为什么不用现成的 ERP / 店小秘 / 船长 BI？**
A：它们做订单聚合与报表展示，费率是内置的少数模板。日本按三边和查档、东南亚续重取整、佣金最低收费，这些要么不支持要么只能填一个固定比例。我要的是"规则可建模、可版本化、可复现"，这在其产品边界之外。

**Q3：为什么不接平台 API 拉真实数据？**
A：开放接口需要开发者资质与店铺授权，个人店已停业，拿不到；且 API 字段与结算账单口径并不一致，真实对账以账单为准。折中做法是按真实报文结构写导入适配器 + 本地样本文件，接口形态可落地，只是换数据源。

**Q4：为什么用双时态，而不是简单加个版本号？**
A：版本号只有一条时间轴，把"业务生效"和"系统记录"混为一谈。补录、修正、追溯调整三种场景下两者必然分叉：一条 3 月生效的规则可能 2 月录错、3 月 5 日才修正。要回答"当时系统认为什么"，两个维度都得能定位。

**Q5：数据是真的吗？**
A：业务背景真实（平台、品类、单量、停业时间），费率按平台公开文档填（Amazon 佣金表、Shopee 费率页、UPS Zone Chart、ヤマト料金表），合同折扣与部分参数为拟真造数。项目固化的是规则结构与算法，不是具体数字，费率过时不影响结论。

**Q6：为什么不用 MQ 做实时计算？**
A：核算不是流式问题：账单按日/周导入、重算按需触发，几十单量级同步算完不到一秒。引入 MQ 只会把"算错了"变成"异步算错了更难查"。架构位置留了（RabbitMQ 异步导入、PowerJob 分片重算），触发阈值写在演进路线里，当前量级降级单机实现。

**Q7：规则录错了怎么修？**
A：不 UPDATE。新增一条 `recorded_at` 更晚的记录，旧版本 `superseded_by` 指向它，valid time 保持不变。这样"修正"本身成为一次可追溯事件，之前基于错误规则算出的账仍可复现，也能对比"修正前后差多少"。

**Q8：未归因或算不出来的订单怎么办？**
A：分两类。规则缺失或参数越界 → 直接失败并标注缺哪条规则，不允许兜底估一个数；定价目标不可达（核价上限低于所需售价）→ 输出缺口金额。原则是宁可报错也不静默近似——静默近似正是当初亏钱的原因。

**Q9：这个项目最难的地方是什么？**
A：不是写代码，是把三种运费结构、四类费用算法归到一个模型里还不丢精度。难的全在边界：三边和 80cm 到底归 80 档还是 100 档，0.2 + 0.4 的 double 累加会多算一个续重，邮编 `00501` 存 int 变 `501` 导致 Zone 全错。这些都不是架构问题，是必须逐个钉死的口径问题。

**Q10：如果重做会怎么改？**
A：三件事。先定口径再建模型——我最初先写实体后补边界，返工最多；费率快照第一天就做成不可变值对象贯穿全程，别中途改成"传到哪算到哪"；核价上限这类外部约束独立成不可行性分析，而不是塞在求解器里返回 null。

## 6. 两个踩坑复盘

### 坑一：浮点误差让续重多收一个

东南亚走首重 0.5kg + 续重 0.1kg。一个订单两件货，0.2kg 和 0.4kg，合箱后总重 0.6kg，应计 1 个续重。但重量是按件累加的：`0.2 + 0.4 = 0.6000000000000001`，减首重得 `0.10000000000000009`，除以 0.1 得 `1.0000000000000009`，`ceil` 就进了 2——多收一个续重。账单对不上，翻三天才查出。修法：全链路改整数克，600 − 500 = 100，100 ÷ 100 = 1，并用 ArchUnit 把 `double`/`float` 挡在计价路径外。

### 坑二：直接 UPDATE 费率表，历史账跟着变了

Shopee 马来站佣金 5%→6%，我在费率表上直接 UPDATE 了 rate 字段，历史账全变。当时没察觉，直到想复盘"3 月那批货按当时费率该定价多少"，重算结果和笔记对不上——旧费率已不存在。这才明白规则也要时间维度：改成只追加不修改，旧版本 `superseded_by` 指向新版本，valid time 与 `recorded_at` 分两轴。
