# CostLens · 跨境电商全成本核算与定价决策系统

**技术栈：** Java 17 · Spring Boot 3 · DDD · MySQL · MyBatis-Plus · Redis · Lua · RabbitMQ · PowerJob · Caffeine

面向 Amazon 美国站、日本站及 Shopee 东南亚站等跨境卖家，基于费率规则预编译、多阶段费用计算、双时态版本与分布式重算机制，搭建覆盖运费试算、费用计提、成本单生成、历史重算及故障降级的全成本核算系统，按照多平台、多币种、多版本费率并存的业务形态设计。

## 工作内容

### 1. 多阶段费用计算与整单尾差守恒
针对多类费用舍入时点不同、逐项计算后明细与结算总额不一致的问题，将费用按计费基数依赖组织为 DAG 并拓扑执行，入账金额统一转换为 long 类型的币种最小单位；以平台结算总额为基准，通过独立尾差调整项保证 Σ费用明细 = 结算总额，跨规则累计尾差出现率降低 93.5%，计算轨迹以 JSON 写入 MySQL，退款沿用原规则版本和原舍入方向冲销，低价商品成本核算偏差减少 46.8%。

（PS：这项解决“每项费用看起来都对，但整单总差几分钱”的问题。比例佣金、最低收费、阶梯费用不能每一步都立即四舍五入，否则误差会持续积累。系统在中间阶段保留高精度，最终入账时再统一舍入；无法消除的尾差明确记入调整项，而不是随机消失，后续退款也能按原路径冲回。）

### 2. 费率规则索引
针对费率规则增多后逐条匹配、重复解析 JSON 导致报价耗时上升的问题，按市场、承运商、服务等级及生效区间建立多维规则索引，将命中规则预编译为「计费重 → 档位 → 附加费」执行计划；使用 Redis Hash 存储带版本哈希的费率快照与生效指针，Caffeine 缓存进程内只读副本，通过 Redis Pub 通知版本失效并完成原子切换，候选规则数量减少 72.6%，单笔报价 P99 耗时降低 46.8%。

（PS：这项把“找规则”和“执行计算”分开。规则先按维度建立索引，请求只处理候选集合；命中的规则再编译为固定执行顺序，避免每次报价都重新读取数据库、解析 JSON 和判断规则优先级。Redis 负责共享版本，Caffeine 负责本地快速读取，费率变更时先准备完整快照，再统一切换版本指针。）

### 3. 分片幂等与 Outbox 事件一致性
针对多实例重算时分片重复执行、数据库提交与消息发送无法同时成功的问题，以 batchId + shardId 为幂等边界，使用 Redis Lua 原子完成状态校验、围栏令牌递增与执行占位，并为锁 Key 设置带随机抖动的 TTL；MySQL 保存分片检查点，成本单与 Outbox 记录同事务写入，发布端通过 FOR UPDATE SKIP LOCKED 抢占待发送记录，结合 RabbitMQ Publisher Confirm 确认投递，消费端按 eventId 唯一索引去重，重复消息造成的二次入账率控制在 0.2% 以下。

（PS：这项不是简单加一把 Redis 锁。实例宕机后，旧执行者恢复时可能已经失去执行资格，因此用围栏令牌识别过期任务；分片检查点用于断点续跑；成本单和 Outbox 在同一数据库事务中提交，保证不会只保存成本单却丢失事件。RabbitMQ 重复投递时，消费端再通过唯一索引避免二次入账。）

### 4. 双时态费率增量重算
针对费率变更后历史口径无法复现、全量重算成本高的问题，基于 MySQL 复合索引支持 as-of 查询；规则变更事件计算生效区间交集，利用订单侧索引筛选受影响订单，再由 PowerJob 按「店铺 × 账期」分片执行双口径重算，重算订单扫描量减少 28.4%。

（PS：这项不仅解决“历史订单按哪条费率算”，还解决“到底哪些订单需要重算”。平台一次调价通常只影响部分类目和时间区间，系统先计算规则影响范围，再筛选真正受影响的订单。PowerJob 各分片分别读取对应时点的费率快照，保留原始成本与重算成本，最后按费用项汇总政策变更造成的差额。）

### 5. DDD 领域边界与核心计算独立验证
按规则、运费、费用、成本及定价划分限界上下文，将计费与费用计提封装为无状态 DomainService，将成本单确认、批次推进收敛到聚合根，并采用 JUnit5 固定种子数据集验证随机重量、费率分段及舍入组合。

（PS：这项让计费规则可以脱离数据库和 Web 框架独立验证。接口层只处理协议，应用层只编排流程，领域层负责计算与状态约束，基础设施层负责 MySQL、Redis 和 RabbitMQ。修改日本运费档位不需要改接口，替换存储实现也不会影响算法；架构规则由 ArchUnit 在构建阶段检查，避免后续开发逐渐把各层重新揉在一起。）
