# CostLens 业务方案

> 跨境电商全成本核算与定价决策系统

---

## 一、项目定位

### 1.1 一句话

> **跨境卖家卖一单能赚多少，取决于三件事：运费怎么算、平台抽多少、政策什么时候变的。这三件事在任何一套现成工具里都算不准——所以我写了一个只做"算准"这件事的系统。**

### 1.2 边界

| 做 | 不做 |
|---|---|
| 成本核算（运费 + 平台佣金 + 支付手续费 + 仓储 + 广告） | 订单管理、库存管理、刊登、物流轨迹 |
| 费率规则建模与版本管理 | 接平台开放平台 API 拉数（用账单导入替代） |
| 毛利还原与亏损归因 | 财务凭证、报税、审计报表 |
| 定价反推与核价约束判断 | 广告投放策略、选品推荐 |

**判断标准**：只做"算得准"与"算得清"，不做"卖得动"。凡是不能落到一个金额数字上的功能，都不进这个项目。

---

## 二、背景

### 2.1 经历

| 项 | 内容 |
|---|---|
| 时间 | 2022.9 – 2023.4（大二） |
| 平台 | Amazon 美国站、Amazon 日本站、Shopee 马来西亚/泰国/印尼站 |
| 品类 | 手机壳、Type-C 数据线、桌面收纳盒（轻小件，客单价低） |
| 单量 | 月均约 40 单（美国 25 / 日本 10 / 东南亚 5） |
| 发货 | FBM 自发货；美国走 UPS Ground，日本走ヤマト宅急便，东南亚走 Shopee SLS |
| 头程 | 云途 / 燕文 空运小包到海外仓 |
| 结果 | **2023 年 4 月停业，直接原因是毛利算成了负数** |

> 以下业务数据按公开费率与个人经历拟真，用于支撑方案设计；真实项目落地时按实际账单替换。

### 2.2 停业的真实原因

不是卖不动，是**算不清**。具体表现：

1. 定价时用"采购价 + 一个估的运费 + 平台大概抽 15%"，估出来的毛利看起来有 20%；
2. 月底看实际账，毛利是负的；
3. 想知道哪一项亏了，只能翻 Excel、对账单，翻三天也说不清；
4. 三个市场三套规则，改一个参数要重算三张表，最后放弃。

**核心矛盾**：卖家不是不想算准，是**没有能力处理正交的多维规则**。

## 三、统一立论

四个痛点看起来分散（运费、佣金、政策变更、定价），但根子是同一个：

> **同一笔成本，在不同平台、不同计算范式、不同时点，算出的结果互不相同；没有一套模型能统一，所以记账必然混乱。**

这句话可以进一步拆成三个"正交性"：

| 正交维度 | 含义 | 对应痛点 |
|---|---|---|
| **计算范式正交** | 不同市场对"运费"的定义不同：美国按重量×距离，日本按体积查表，东南亚按重量分段取整 | P1 |
| **计算维度正交** | 不同费用项的计价因子不同：佣金按类目×金额，运费按重量×分区，支付费按比例+定额 | P2 |
| **时间口径正交** | 同一规则在不同时点取值不同，历史账不能套用现行规则 | P3 |
| **决策方向正交** | 成本是"由因推果"，定价是"由果推因"，后者是方程不是加法 | P4 |

**四个亮点就是把四个正交维度各解一遍。** 这不是四个模块拼盘，是一条论证链。

## 四、四个痛点与四个亮点

### P1 · 运费计费范式异构

#### 痛点

三个市场的运费规则不是"参数不同"，而是**数学结构不同**：

| 市场 | 主计价因子 | 数学结构 | 公式 |
|---|---|---|---|
| 🇺🇸 Amazon 美国站 / UPS Ground | 计费重（实重 vs 体积重取大） | **连续线性** | `费用 = 计费重(进位0.5kg) × Zone单价(重量段)` |
| 🇯🇵 Amazon 日本站 / ヤマト宅急便 | 三边和（长+宽+高） | **阶跃查表** | `Size档 = lookup(三边和) → 费用 = 表(地帯, Size档)`，重量仅做上限校验 |
| 🇹🇭 Shopee SLS 东南亚 | 实重（体积重不启用） | **分段 + 向上取整** | `费用 = 首重价 + ceil((实重−首重)/续重单位) × 续重价` |

#### 真实案例

日本站一票货，三边和 79.5cm。我按 60 档（≤60cm）报价，实际被按 80 档收，运费比售价还高。

东南亚一票 0.7kg。首重 0.5kg，续重单位 0.1kg。理论上该收 7 个续重，账单上收了 8 个。

#### 为什么必须抽象而不是配置

很多人会想"用一张配置表，字段多一点就能覆盖"。这条路走不通，因为：

1. **计价因子不同**：美国看"重量"，日本看"三边和"，东南亚看"实重"。字段集合都不一样；
2. **重量角色不同**：美国重量直接计价，日本重量只是上限约束（超了才升级档），东南亚重量驱动分段取整；
3. **体积重概念不通用**：美国是核心因子，日本不存在这个概念，东南亚不启用。

强行合并成一张宽表，会退化成 EAV 反模式：大量 NULL 字段 + 语义靠注释维护 + 每加一个市场改一次表结构。

#### 方案：计费策略族

```java
public interface FreightRateStrategy {
    FreightQuote quote(ShipmentContext ctx, RateCardSnapshot card);
}

// DimWeightZoneStrategy      美国：重量 → 阶梯单价 × Zone
// GirthSizeBandStrategy      日本：三边和 → Size 档 → 地帯价，重量仅校验上限
// FirstAddWeightStrategy     东南亚：首重 + 续重向上取整
```

三个实现 + 三张独立费率表。加市场 = 新增一个实现类 + 一张表，**不动主流程**。

#### 关键边界（真正的功夫）

| 市场 | 坑 | 做法 |
|---|---|---|
| 🇯🇵 档位边界 | 三边和恰好 80.0cm 归 80 档还是 100 档；实测尺寸带小数时，先累加再取整会整体偏移一档 | 显式定义「含上界」，输入先向上取整到整数厘米，用 79/80/81 三组用例锁死 |
| 🇹🇭 续重个数 | 两件货 0.2kg + 0.4kg，double 累加得 `0.6000000000000001`，减首重后除以 0.1 得 `1.0000000000000009`，`ceil` 进 2，**多收一个续重** | 整数克运算：600g − 500g = 100g，100 ÷ 100 = 1 |
| 🇺🇸 体积重 | 139（英寸体系）vs 5000（厘米体系）用错差 20%；逐件进位 vs 整票进位 | 单位显式归一 + 进位策略化 |
| 🇺🇸 邮编 | `00501` 存成 int 变 `501`，Zone 全错 | 邮编保持字符串 + 区间索引 |

**统一铁律**：金额用整数最小单位（USD 分 / JPY 円），重量用整数克，尺寸用整数厘米；ArchUnit 禁止 `double`/`float` 进入计价路径。

### P2 · 平台费用异构核算

#### 痛点

佣金不是"售价 × 固定比例"。真实规则至少四类，且互相正交：

| 费用项 | 规则类型 | 真实细节 |
|---|---|---|
| 平台佣金 | 比例 + **最低收费** + **分段** | Amazon 美国站：多数类目 15%，电子产品 8%，服装 17%；**每笔最低 $0.30**；服装类目 **$250 以上部分仅按 5%** 计提 |
| 支付手续费 | 比例 + **固定额** | PayPal 跨境约 4.4% + 固定费；Stripe 2.9% + $0.30；收款通道提现另计 |
| 仓储费 | 按体积 × 时间 | 月度仓储费按时段单价，长期仓储费另计 |
| 广告费 | 按点击 | CPC 竞价，与上述全部正交 |

#### 最容易被忽略的一点：最低收费会让实际费率翻倍

设商品售价 $1.00，类目费率 15%：

```
按比例应计：$1.00 × 15% = $0.15
最低收费：$0.30
实际计提：max($0.15, $0.30) = $0.30
实际费率：$0.30 / $1.00 = 30%
```

**名义 15%，实际 30%。** 卖低价轻小件的卖家（手机壳、数据线），几乎全部踩在这个坑上。这正是"毛利表看起来有 20%、实际是负的"的直接来源之一。

#### 第二个坑：分段计费

Amazon 服装类目，$250 以内按 17%，**超过 $250 的部分按 5%**。

```
售价 $300：
  前 $250 × 17% = $42.50
  后 $50  × 5%  = $2.50
  合计 = $45.00（等效费率 15%，不是 17%）
```

单一"费率 × 售价"模型在任何一个分界点都会算错。

#### 方案：统一费用项模型

把所有费用抽象成 `CostItem`，每个项绑定一条 `ChargeRule`：

| 规则类型 | 语义 | 参数 |
|---|---|---|
| `Percentage` | 金额 × 费率 | rate |
| `PercentageWithFloor` | max(金额 × 费率, 最低额) | rate, floor |
| `TieredByAmount` | 按金额区间分段，各段不同费率 | segments[] |
| `PerUnitByMeasure` | 按件数 / 体积 / 重量计价 | unitPrice, measure |

- 一笔订单的总费用 = Σ 各 `CostItem` 计算结果，**每项独立计算后汇总，不做中间合并**（合并会丢精度也会丢可解释性）
- 支持 `cap`（封顶）与 `mutexGroup`（互斥，如"参加活动免佣金"与"活动服务费"不可同时生效）
- 输出明细到单据级：`订单 → 费用项 → 规则版本 → 计算过程`，任何一分钱都能钻取

#### 关键设计：正向计费 vs 反向计提

这是本模块与 P1 的本质区别：

| | 运费（P1） | 平台费用（P2） |
|---|---|---|
| 计算方向 | **正向**：已知重量尺寸 → 算金额 | **反向**：已知售价金额 → 计提费用 |
| 依赖 | 与订单金额无关 | **依赖订单金额**，而金额本身又受费用影响（定价时要解方程） |

这个"反向计提"的特性，直接把 P2 接到了 P4（定价反推）：**费用是售价的函数，所以定价无法直接除算**。

### P3 · 费率政策变更导致历史账失真

#### 痛点

平台费率会变。Shopee 某站点佣金从 5% 调到 6%，Amazon 调整配送费，承运商调整燃油附加费。

问题不是"变了以后怎么算"，而是**变了以后，历史账怎么办**：

1. **复盘失真**：想回答"如果按新费率，我 3 月那批货该定价多少"——但不能直接用新规则覆盖旧账，因为 3 月的定价是基于旧费率的；
2. **追溯调整**：平台补扣或退费，要求在**原账期**上做调整，而不是在当前期记一笔。否则月度毛利曲线会跳变，看不出真实经营趋势；
3. **规则录错**：费率录进去发现录错了，想改。但如果直接 UPDATE，历史重算结果会变，之前基于错误费率做的决策就永久失去可复现性。

#### 立论

> **"规则"和"数据"一样，都需要时间维度。只有 business time 的模型，无法回答"我当时是怎么认为的"。**

#### 方案：双时态（bitemporal）版本模型

两个独立时间轴：

| 时间轴 | 含义 | 例子 |
|---|---|---|
| **valid time**（业务生效时间） | 这条规则在业务上从什么时候到什么时候有效 | `2023-01-01 ~ 2023-06-30，费率 5%` |
| **transaction time**（系统记录时间） | 系统是什么时候知道这件事的 | `2023-02-10 录入，2023-03-05 修正过一次` |

规则表结构（核心字段）：

```
platform_fee_rule
  rule_id           规则身份（同一规则的所有版本共享）
  version_seq       版本序号
  valid_from        业务生效起
  valid_to          业务生效止
  recorded_at       系统记录时点  ← transaction time
  superseded_by     被哪个版本取代（NULL 表示当前有效）
  ...
```

**三条铁律**：

1. **只追加，不修改**：改规则 = 插入一条新版本，把旧版本 `superseded_by` 指向新版本；
2. **修正也走新增**：发现录错了，新增一条 `recorded_at` 更晚的记录，而不是 UPDATE；
3. **as-of 查询必须双时间**：既问"业务上哪天有效"，也问"系统当时是怎么认为的"。

#### 两种查询能力

| 查询 | 问法 | 用途 |
|---|---|---|
| **业务时点查询** | "2023-03-15 这一天，适用哪条费率？" | 日常核算 |
| **认知时点查询（as-of）** | "截至 2023-03-20，系统认为 2023-03-15 适用哪条费率？" | 审计复现、复盘"当时为什么这么算" |

#### 双口径重算

重算任务支持两种口径，结果并排展示：

| 口径 | 使用规则 | 回答的问题 |
|---|---|---|
| **原时点口径** | 按订单发生时的有效规则 | 当时算得对不对？ |
| **现行口径** | 按当前最新规则 | 如果明天重跑一遍，会差多少？ |

两者之差 = **政策变更对历史成本的影响额**，可以按费用项拆解，直接指出"这次调价让你多付了多少"。

### P4 · 定价无法反推

#### 痛点

成本算准了，定价还是拍脑袋。因为定价是个**方程**，不是加法：

```
目标：售价 − 采购成本 − 运费 − 佣金(售价) − 支付费(售价) − 广告 − 仓储 = 目标毛利
```

其中 `佣金(售价)` 和 `支付费(售价)` 都是售价的函数，而且：

1. 佣金含**最低收费**：`佣金 = max(售价 × 费率, $0.30)` → 分段函数；
2. 佣金含**分段**：服装类目超过 $250 部分按 5% → 分段函数；
3. 支付费是**比例 + 固定额**：`支付费 = 售价 × 费率 + 固定费`。

所以 `f(售价) = 0` 是一个**分段函数方程**，不能直接 `售价 = 成本 / (1 − 费率)`。

#### 真实后果

用简单除算法定价，在低价区间会系统性高估毛利（因为忽略了最低收费），定价偏低 → 卖得越多亏得越多。我的手机壳生意就是这么亏的。

#### 方案：分段方程求解

求解流程：

```
1. 枚举所有可能的价格分段（由 TieredByAmount 的分界点 + 最低收费的临界点共同决定）
2. 对每个分段：假定解落在该段内，用解析法化简（段内 f 是线性的），直接求解
3. 验证：解是否落在假定区间内
   - 落在区间内 → 命中，返回
   - 不在区间内 → 该段无解，换下一段
4. 全部段枚举完仍无解 → 报告"目标毛利不可达"并给出最接近的可达点
```

**最低收费的退化处理**：当 `售价 × 费率 < floor` 时，佣金恒为 `floor`，此时 `f` 在该区间退化为线性，可以直接解；解出后必须校验 `售价 × 费率 < floor` 是否成立，不成立则说明假设错误，重算。

#### 约束：平台核价上限

Temu 等平台的核价机制会给一个价格上限（同款价格分位）。定价必须满足双约束：

```
求解售价 x*，使得 f(x*) = 0
且 x* ≤ 核价上限
```

若 `x* > 核价上限`，则该品在这个平台**不可行**，输出缺口金额（"还差 ¥3.20 才能达到 25% 毛利"），而不是静默返回一个达不到目标的价。

**输出"不可行"比输出一个错误的价格更有价值**——这是本模块的设计原则。

## 五、量化指标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 三市场计费边界用例通过率 | **100%** | 档位边界 80 例 + 续重边界 60 例 + Zone 边界 40 例 |
| 续重个数计算准确率 | **100%** | 0.5 / 0.6 / 0.7 / 0.71 / 1.0 / 1.01 kg 等 60 组边界 |
| 费用项算法覆盖 | **4 类全覆盖** | 比例 / 比例+最低收费 / 金额阶梯 / 按件按体积 |
| 最低收费偏差 | **0**（此前低价品最高 100%） | $0.50–$3.00 区间 50 组商品逐项校验 |
| 双时态 as-of 查询正确性 | **100%** | 20 组"规则变更 + 修正"场景，可复现任一历史认知状态 |
| 双口径重算差异可定位 | **100%** | 政策变更场景，差异可拆解到费用项级 |
| 定价分段求解收敛率 | **1000 组随机参数全部收敛** | 覆盖含最低收费、含阶梯、含封顶的组合 |
| 核价不可行场景识别率 | **100%** | 约束冲突场景均输出缺口金额，无静默近似 |

> 所有指标为**确定性计算的可穷举验证**，不依赖压测，不涉及并发。这个项目衡量的是**正确性**，不是吞吐。

## 六、诚实边界

必须主动说明的三件事：

1. **数据为拟真造数**。业务背景（平台、品类、单量、时间）按真实经历编写，费率数值按平台公开规则填写，合同折扣与部分参数为虚构。
2. **不做真实上线**。不接平台开放平台 API，不接真实收款通道。账单用适配器 + 本地样本文件模拟，但适配器接口按真实报文结构设计。
3. **费率数值会过时**。平台费率以官方最新公告为准，本项目固化的是**规则的结构与算法**，不是具体数字。

**为什么这些边界不影响项目价值**：

- 平台费率规则是**公开可查**的（Amazon 佣金表、Shopee 费率页、UPS Zone Chart、ヤマト料金表），面试官可自行核对；
- 最容易被质疑的"最低收费""分段计提"等细节，都有平台官方文档支撑；
- 项目的技术含量在**规则建模能力**（如何把异构规则统一抽象）和**精度正确性**（如何保证一分钱都不差），这两点不依赖真实数据。

## 七、演进路线

按数据量给出引入中间件的触发阈值，避免"为技术栈而技术栈"：

| 量级 | 需要引入 | 触发原因 |
|---|---|---|
| 月 < 500 单（当前） | MySQL + 进程内缓存 | 单机足够 |
| 月 5k 单 | Redis 缓存费率快照 + 幂等锁 | 费率查询 QPS 上升，快照重复加载 |
| 月 5 万单 | RabbitMQ 异步导入账单 + 索引优化 | 账单文件变大，同步导入超时 |
| 月 50 万单 | PowerJob 分片重算 + 差异宽表入 ES | 历史重算窗口拉长，单机跑不完 |

**当前实现选择**：保留 Redis / RabbitMQ / PowerJob 的架构位置与接口设计，但在文档中明确标注"当前量级可降级为单机实现"，保证架构可演进而不超前。

## 八、术语表

| 术语 | 含义 |
|---|---|
| valid time | 业务生效时间：规则在业务上何时有效 |
| transaction time | 系统记录时间：系统何时知道这条规则 |
| as-of 查询 | 还原某一历史时点系统所认知的状态 |
| 计费重 | 实重与体积重取大者，用于运费计价 |
| 体积重 | 长×宽×高 ÷ 抛比，反映占用舱位 |
| 抛比 | 体积重除数：空运 6000、快递 5000、海运 1000 |
| 三边和 | 长+宽+高，日本宅急便按此分 Size 档 |
| Size 档 | ヤマト宅急便的尺寸档位：60/80/100/120/140/160/180（cm） |
| Zone | 邮编分区，美国运费按距离计价的基础 |
| 最低收费（floor） | 按比例计算不足最低额时按最低额收取 |
| 核价上限 | 平台对商品售价的上限约束（同款价格比对结果） |
